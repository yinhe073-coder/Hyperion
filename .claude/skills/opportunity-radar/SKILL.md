# 机会雷达

代码在仓库的 `opportunity-radar/` 目录，所有命令都在该目录下运行，Node 20+，无需安装依赖。
你在这里的角色是**评估者**：脚本负责采集和生成文件，判断哪些信号值得做、以及写落地页和发帖文案，由你完成。

## 每日流程

1. **统计在跑的实验**：`node radar.js track`
2. **采集**：`node radar.js collect`，然后读 `data/candidates.json`（含 `runId` 和最多 30 条候选）。
3. **评估**：读 `config.json` 里的 `profile.about`（用户画像），对每一条候选给出结论，写入 `data/evaluation.json`。格式见下文。
4. **生成**：`node radar.js build`。它会校验你的评估文件，不合格会列出具体错误，按提示改完重跑。
5. **汇报**：读生成的日报（路径在 `data/last-report.txt`），用几句话告诉用户：今天有没有值得做的、各自的第一步是什么、有哪些实验待批准或有新线索。

如果环境里有 `ANTHROPIC_API_KEY`，`node radar.js run` 会一次跑完全部步骤并由 API 完成评估；没有密钥时按上面的步骤由你来评估。

## 评估标准

按重要性排序：

1. 需求是否真实且反复出现。一个人的随口抱怨不算。
2. 是否有明确的付钱方，以及他们现在是否已经在为替代方案花钱或花时间。
3. 用户能否在 48 小时内做出一个可以收钱或收集预订的最小版本。
4. 是否能说出具体的获客渠道。

对走红的产品（`kind: "proof"`），考虑的是切更小的人群、做中文或本地化版本、做配套工具或代跑服务，而不是原样照抄。

**从严**：大多数应该是「观察」或「放弃」。「做」每次最多 2 条，没有合适的就一条都不给——宁可空着，不要凑数。涉及版权、越狱、灰色地带的一律「放弃」。

## data/evaluation.json 格式

```json
{
  "runId": "<原样复制 data/candidates.json 里的 runId>",
  "evaluator": "claude-code-skill",
  "items": [
    {
      "id": "<候选的 id>",
      "verdict": "做 | 观察 | 放弃",
      "score": 0,
      "opportunity": "一句话：赚钱机会是什么",
      "who_pays": "谁付钱、大概愿付多少",
      "mvp_48h": "48 小时内能做出的最小可卖版本",
      "first_step": "今天就能做的第一个验证动作",
      "risk": "最可能让它失败的一个原因",
      "kit": { "仅 verdict 为「做」时提供，见下": "" }
    }
  ]
}
```

- 每条候选都要有一项；`score` 是 0–100 的整数；所有文字字段用简体中文，一两句话，具体到能照做。
- 「放弃」的条目各字段可以很短，`risk` 写放弃的原因。

### kit（只给「做」的条目）

脚本用它生成落地页 `drafts/<slug>/index.html` 和发帖草稿 `drafts/<slug>/posts.md`。

| 字段 | 内容 |
|---|---|
| `slug` | 网址短名，3–40 位小写字母、数字、连字符 |
| `name` | 产品或服务的名字 |
| `headline` | 落地页主标题：给谁、解决什么问题 |
| `subhead` | 一两句话说明怎么解决 |
| `bullets` | 3–5 条具体好处（数组） |
| `price` | 计划定价，写具体数字，例如「计划定价：单条 19 元」 |
| `cta` | 按钮文字，例如「加入候补名单」 |
| `audience` | 适合谁 |
| `channels` | 2–4 个具体的社群或版块（数组） |
| `post_title` / `post_body` | 社群发帖的标题和正文，正文用 `{{LINK}}` 代表落地页链接 |
| `reply_draft` | 回复原帖的草稿 |
| `dm_draft` | 私信模板 |

写文案的规矩：

- 这是产品做出来**之前**的预约页。不要写成产品已经存在，不要编造用户数、好评、案例或任何数据。
- 标题说人话，不要口号。
- 发帖草稿要像真人在分享和征求意见：先讲问题和自己的做法，再给链接。
- 回复原帖要先真正回应对方的问题；如果信号来自开源仓库，先确认协议并征得作者同意。
- 私信模板要短，先问对方现在怎么解决，不要一上来推销。

## 实验管理

| 用户想做的事 | 命令 |
|---|---|
| 看所有实验的状态 | `node radar.js status` |
| 批准某个实验上线 | `node radar.js approve <slug>` |
| 改了收集方式后重新生成草稿 | `node radar.js rebuild` |
| 统计线索并下结论 | `node radar.js track` |

- 批准前必须在 `config.json` 的 `landing.formAction`（表单后端地址）或 `landing.contactEmail` 里至少配置一个，否则脚本会拒绝。这两个值由用户决定，不要替用户填。
- 线索记录在 `landing.leadsSource` 指向的 CSV（默认 `data/leads.csv`，表头 `date,slug,type,note`，`type` 为 `lead` 或 `paid`）。用户告诉你有人预约或付款时，往里加一行。
- 结论规则在 `config.json` 的 `validation`：默认 48 小时内 ≥1 人付款或 ≥5 条线索为「放大」；有线索但不够则延长一次；否则「停」并下线落地页。

## 边界

- **不要替用户对外发布任何内容**：不发帖、不发私信、不开 Issue 或 Discussion。只生成草稿，由用户本人审阅后发出。
- 只有用户明确说要批准时才运行 `approve`。
- 运行后文件有变化时，按用户的习惯决定是否提交；不要自行推送到默认分支。
- 汇报时如实说明：评估是基于公开帖子的判断，不是对收入的保证。
